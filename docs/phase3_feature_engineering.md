# Phase 3: Feature Engineering

Phase 2에서 보류했던 두 가지 결정 사항 정리. **둘 다 최종 결정은 보류 — 분석 결과와 후보만 제시.**

## 1. 시계열 활용 방식 추천

Phase 2 §5에서 제시한 4가지 옵션(A: 최근 1개월 / B: 월별 집계 통계량 파생 / C: 최근 N개월 요약 / D: 시퀀스 모델)에 대한 의견.

**조건**: 고객 5만 명 규모, 다음 모델은 LightGBM/XGBoost 등 트리 계열 우선, Phase 4에서 SHAP 해석이 목표.

### D(시퀀스 모델)는 지금 단계에서 제외를 권장 — 사용자 의견에 동의
- 트리 모델은 애초에 시퀀스를 직접 입력받지 못하므로, D를 쓰려면 RNN/Transformer 등 완전히 다른 모델링 트랙을 병행해야 함 → "트리 계열 우선"이라는 다음 단계 방향과 자체로 안 맞음
- Phase 4 목표가 SHAP 기반 해석인데, 시퀀스 모델은 SHAP 적용이 훨씬 까다롭고(TreeExplainer 같은 성숙한 도구가 없음) 해석 가능성이라는 포트폴리오 취지와도 어긋남
- 5만 표본 규모에서 시퀀스 모델은 과적합 위험도 큼
- → D는 Phase 8 이후 "확장 아이디어"로 문서에만 남기고 지금은 보류하는 게 맞다고 봄

### A vs B vs C 추천: **B (월별 집계 통계량 파생) 중심, A는 baseline으로 병행**
이유:
1. Amex Kaggle 대회 자체가 실제로 이 방식(고객별 mean/std/min/max/last/first, last-first delta 등 파생)이 표준 접근으로 자리잡았던 대회임 — 트리 모델 + 집계 파생 조합이 이미 검증된 조합
2. 데이터 규모(5만 명 × 188 feature × 13개월)에서 집계 연산 자체는 DuckDB로 몇 초면 끝나는 수준이라(Phase 1~2에서 이미 확인) 계산 비용이 C를 택할 이유가 되지 못함
3. 트리 모델(LightGBM/XGBoost)은 feature 수가 188 × (통계량 개수)로 늘어나도(수백~천 단위) 잘 처리하고, feature importance/SHAP으로 자연스럽게 걸러낼 수 있음
4. 다만 **전체 통계량을 다 만들면 과할 수 있어서**, 처음부터 mean/std/min/max/last/first/slope(last-first) 전부보다는 **mean, std, last, last-first delta** 정도로 시작하는 걸 제안 — "최신 상태"(last)와 "추세"(delta)를 동시에 잡으면서 feature 수는 188×4=752 정도로 통제됨. SHAP 요약을 포트폴리오에 담을 때도 이 정도가 설명하기 수월함
5. A(최근 1개월만)는 그 자체로 최종 방식이라기보다, **B/C 파생 feature들과 성능을 비교할 baseline 모델**로 병행하는 걸 추천 — "시계열 파생이 실제로 baseline 대비 얼마나 개선되는지"를 포트폴리오에서 보여줄 수 있는 좋은 비교 지점이 됨

**요약 추천**: baseline = A, 본 모델 = B(mean/std/last/delta로 축소한 버전), C는 필요시(과적합/차원 문제 발생 시) 대안으로 남겨둠, D는 지금 단계 제외.

## 2. D_49/D_132/D_106, D_134~D_138 상관관계 확인 — **가설이 틀렸음을 확인**

### 방법
8개 컬럼을 pandas로 pairwise Pearson correlation 계산 (결측은 pairwise exclude).

### 결과: 실제 값 상관관계는 전부 낮음 (최대 0.249, 0.95 근처도 없음)

|        | D_49 | D_132 | D_106 | D_134 | D_135 | D_136 | D_137 | D_138 |
|---|---|---|---|---|---|---|---|---|
| D_49  | 1.000 | -0.032 | 0.249 | 0.123 | -0.029 | 0.008 | -0.002 | -0.015 |
| D_132 | -0.032 | 1.000 | 0.011 | 0.066 | -0.014 | -0.034 | -0.029 | -0.083 |
| D_106 | 0.249 | 0.011 | 1.000 | 0.069 | -0.022 | 0.066 | -0.004 | -0.035 |
| D_134 | 0.123 | 0.066 | 0.069 | 1.000 | 0.004 | 0.020 | -0.004 | 0.014 |
| D_135 | -0.029 | -0.014 | -0.022 | 0.004 | 1.000 | -0.050 | -0.002 | -0.079 |
| D_136 | 0.008 | -0.034 | 0.066 | 0.020 | -0.050 | 1.000 | -0.092 | -0.504 |
| D_137 | -0.002 | -0.029 | -0.004 | -0.004 | -0.002 | -0.092 | 1.000 | -0.015 |
| D_138 | -0.015 | -0.083 | -0.035 | 0.014 | -0.079 | -0.504 | -0.015 | 1.000 |

가장 큰 값도 D_136–D_138 = -0.504, D_49–D_106 = 0.249 수준 — **"값이 거의 동일하다"는 Phase 2 시점의 추측은 틀렸음**. 30개 고결측 컬럼 리스트에서 결측률 수치가 비슷해서 나온 오해였음.

### 진짜 원인: 값이 아니라 결측 "패턴"이 겹치는 것 (block-missing)

| 그룹 | 결측 겹침 정도 |
|---|---|
| D_134, D_135, D_136, D_137, D_138 | **100.00%** 행에서 5개 컬럼의 결측 여부가 완전히 동일 (한 컬럼이 비면 나머지 4개도 항상 같이 빔) |
| D_49 vs D_132 | Jaccard 99.94% |
| D_49 vs D_106 | Jaccard 99.92% |

→ 이 컬럼들은 같은 원본 데이터 소스/섹션에서 "한 번에 채워지거나 한 번에 비는" 구조로 보임(예: 특정 상품·이벤트 관련 항목 묶음). 값 자체는 서로 독립적인 정보를 담고 있어서 **하나를 남기고 나머지를 버리는 건 정보 손실**임.

### 후보 제시 (최종 결정은 사용자)

**value 컬럼 자체는 8개 다 유지를 제안** — pairwise corr이 전부 0.95는커녕 0.5 이하라 중복 근거가 없음. target과의 단순 상관(§Phase2)도 이 컬럼들은 결측률 90%+라 표본이 적어(D_49/D_132/D_106 ~59K행 중 nonnull, D_134~138 ~21K행) corr_target 자체가 약하게 나오는 게 자연스러움(D_49 -0.013, D_132 -0.090, D_106 -0.008, D_134 -0.030, D_135~D_138 ±0.01~0.04) — 이 수치만으로 "덜 중요한 컬럼"이라 판단하기엔 표본이 너무 작아 근거가 약함.

대신 **"결측 여부 indicator" feature를 만들 때는 중복 제거를 제안**:
- D_134~D_138: 5개 각각의 `is_missing` 플래그 대신 **공용 플래그 1개**(`D_134_138_group_missing`)로 통합 — 5개가 100% 동일 패턴이라 나머지 4개는 정보량 0
- D_49/D_132/D_106: 거의 동일(99.9%)하지만 완전 동일은 아니므로, 공용 플래그 1개 + 나머지 차이(0.06~0.08%에 해당하는 행)를 버릴지는 선택 사항 — 정보 손실이 극히 작아 통합해도 무방해 보이지만, 완전 동일은 아니라는 점은 참고

**기준 정리**:
- 1순위 기준(제안): value 컬럼은 pairwise |corr| ≥ 0.95 같은 임계값 초과하는 게 없으므로 **전부 유지**
- 만약 사용자가 그래도 일부를 줄이고 싶다면(예: 차원 축소 목적), 판단 기준 후보:
  - target과의 상관계수 절대값이 더 높은 쪽 유지 (사용자가 제시한 기본 원칙) — 단, 위에서 설명했듯 표본 작아 신뢰도 낮음
  - 결측률이 더 낮은 쪽 유지 (정보량이 더 많음): D_49(90.12%) < D_132(90.17%) < D_106(90.19%) 순으로 D_49가 근소 우위
  - Phase 2 §2의 phi(결측-target 연관성) 기준: D_132(0.232)가 D_49/D_106보다 target과의 결측 연관이 강했음 — 어느 기준을 우선할지에 따라 결론이 달라짐

## 3. 결정 사항 반영 및 feature 테이블 생성

사용자 결정: (1) B(mean/std/last/delta) 메인 + A(최근 1개월) baseline 병행, (2) value 컬럼 8개 전부 유지, (3) 결측 indicator만 정리 — D_134~D_138은 공용 플래그 1개로 통합, D_49/D_132/D_106은 phi 최댓값인 **D_49**(phi=0.2335, D_132 0.2324·D_106 0.2320보다 근소 우위)만 유지.

스크립트: [`scripts/phase3_build_features.py`](../scripts/phase3_build_features.py)

### 3.1 baseline A — 최근 1개월 스냅샷
- `data/processed/train_features_baseline_A.parquet`: 50,000행(=고객 수), 191컬럼(원본 188 feature + customer_ID + target, S_2는 제외), 32MB

### 3.2 main B — mean/std/last/delta 파생 + 정리된 missing indicator
- `data/processed/train_features_main_B.parquet`: 50,000행, **751컬럼**, 168MB
  - 수치형 186개 × 4통계(mean/std/last/delta) = 744
  - 범주형 2개(D_63, D_64) × last = 2
  - 정리된 missing indicator 2개: `D_134_138_missing_frac`(D_134~D_138 대표), `D_49_missing_frac`(D_49/D_132/D_106 대표)
  - `customer_ID`, `target`, `n_months_observed`(참고용, 관측 개월 수)
  - `D_49_missing_frac`/`D_134_138_missing_frac` 값 확인 결과, 개별 고객 사례(Phase 2 §3에서 본 `0000f995...` 고객)와 일치 — 두 지표 모두 1.0(완전 결측)으로 계산됨

### 3.3 메모리 실측 (사용자 요청: 계속 모니터링)
- 시작 시점 여유: 791MB
- **1차 시도(744개 집계 컬럼을 한 번의 GROUP BY로 처리)는 `memory_limit=1GB`에서 953MB 지점에 OOM으로 안전하게 중단됨** — 시스템 자체는 위험하지 않았음(중단 후 unused 927MB), DuckDB가 스스로 설정한 한도를 넘지 않으려 멈춘 것
- 이를 컬럼 40개씩 5개 배치로 나눠 각각 따로 집계 후 마지막에 customer_ID로 join하는 방식으로 재작성
- **재시도 peak RSS: 544MB**, 실행 중 시스템 unused가 순간적으로 95MB까지 떨어졌으나 완료 후 879MB로 회복, swap 사용량 625MB로 **추가 증가 없음** (배치 방식이 안전하게 작동함을 확인)

### 3.4 Quick 벤치마크: baseline A vs main B (LightGBM 기본 하이퍼파라미터, 5-fold CV)

스크립트: [`scripts/phase3_quick_benchmark.py`](../scripts/phase3_quick_benchmark.py). 튜닝 없이 `LGBMClassifier` 기본값 + `StratifiedKFold(5)`로 ROC-AUC만 빠르게 비교 (본격 튜닝/평가는 Phase 4).

| | shape | AUC (5-fold 평균) | std | 소요시간 |
|---|---|---|---|---|
| A (baseline, 최근 1개월) | (50000, 189) | 0.9548 | 0.0020 | 7.2s |
| B (main, mean/std/last/delta) | (50000, 749) | 0.9551 | 0.0010 | 25.4s |

**차이 (B − A): +0.0003** — fold별 표준편차(0.001~0.002)보다도 작은 차이라, 이 quick 체크만으로는 **B가 A보다 뚜렷하게 낫다고 말하기 어려움**. 예상(시계열 파생이 더 많은 정보를 주니 개선될 것)과 다른 결과.

가능한 해석(참고용, Phase 4에서 더 검증 필요):
- baseline A(최근 1개월 스냅샷) 자체의 AUC가 이미 0.9548로 매우 높음 — "최신 상태" 정보량이 이미 커서, mean/std/delta가 주는 추가 정보의 한계효용이 크지 않을 수 있음
- B의 `_last` 컬럼이 A와 사실상 동일한 정보를 이미 포함하고 있어 mean/std/delta가 LightGBM 기본 트리 수(n_estimators=100, 튜닝 없음)로는 아직 잘 활용되지 못했을 가능성
- 5-fold 단순 CV로는 fold 간 std(0.001~0.002) 대비 차이(0.0003)가 노이즈 수준이라 통계적으로 유의미하다고 보기 어려움 — 표본을 늘리거나(현재 5만 명) repeated CV, 또는 Phase 4의 본격 튜닝(learning_rate, num_leaves, early stopping 등)으로 재확인 필요

**결론**: 이번 quick 체크로는 A/B 중 하나를 지금 확정하기보다, **Phase 4에서 둘 다 제대로 튜닝해서 다시 비교**하는 게 맞다고 판단됨. 다만 "일단 A만으로도 상당히 강력한 baseline"이라는 점은 확인됨.

### 3.5 메모리 실측 (벤치마크)
- 시작 시점 여유: 330MB
- **peak RSS 1,828MB** — 지금까지 중 가장 높은 수치 (LightGBM이 749개 feature × 5 fold 학습을 위해 훈련 데이터 + 트리 구조를 메모리에 유지해야 해서, DuckDB 집계 작업들보다 메모리 사용이 큼)
- 실행 중 시스템 unused가 62~104MB까지 떨어졌으나 swap 사용량은 617MB로 **거의 변화 없음**(직전 625MB) — 위험한 수준까지는 가지 않았지만 이번 세션에서 가장 타이트했던 구간
- 완료 후 unused 1,861MB로 회복 (다른 백그라운드 프로세스 메모리 해제와 겹친 것으로 보임)
- **Phase 4에서 본격 튜닝(더 많은 n_estimators, 여러 모델 비교) 시에는 이보다 메모리 사용이 늘어날 수 있어 계속 모니터링 필요**

### 3.6 참고: 다음 단계 시 유의할 점
- `std`는 관측 개월 수가 1개인 고객은 NaN이 됨(표준편차 정의상 자연스러움) — LightGBM/XGBoost 모두 NaN 네이티브 처리하므로 별도 imputation 불필요
- `D_63_last`, `D_64_last`는 아직 문자열(범주형) — Phase 4 모델링 시 원-핫 또는 native categorical 처리 필요
- baseline A와 main B는 서로 다른 컬럼 스키마(191 vs 751)이므로 모델 성능 비교 시 두 데이터셋을 각각 독립적으로 학습해야 함
